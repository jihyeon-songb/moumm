## 1. 요약

Moumm은 인스타그램에서 발견한 맛집·카페가 가볼 만한 곳인지 한 화면에서 판단하도록 돕는 모바일 웹 MVP다. 사용자가 게시물이나 릴스 링크를 붙여넣으면 서버가 공개 메타데이터에서 캡션을 읽고, 장소 후보를 찾아 확인을 받은 뒤, 게시물이 말하는 추천 이유·메뉴·가격·방문 팁과 카카오의 기본 장소 정보를 함께 보여준다.

링크에서 단서를 얻지 못하면 게시물 이미지 1~2장을 OCR로 읽고, 그래도 없으면 캡션 붙여넣기나 직접 검색으로 넘어간다. 자동 분석이 실패해도 사용자가 장소를 직접 찾아 저장할 수 있어야 한다.

첫 버전은 국내 맛집·카페에 한정한다. 장소 데이터와 검색 제공자는 분리해 두되, 해외 확장 설계는 인터페이스 수준에서만 남긴다.

## 2. 문제, 가설, 성공의 정의

### 문제

사용자는 인스타그램에서 장소를 발견한 뒤 메뉴, 가격, 위치, 영업시간을 확인하려고 네이버·카카오·구글 지도를 다시 검색한다. 이 과정이 번거로워 판단을 미루거나 포기한다.

### 제품 가설

게시물에서 뽑은 추천 맥락(추천 이유, 메뉴, 가격, 방문 팁)과 지도 서비스의 기본 장소 정보를 한 화면에 모으면, 사용자가 다른 앱에서 다시 검색하지 않고 저장 또는 관심 없음을 결정할 수 있다.

Phase 0 결과, 지도 서비스의 평점·영업시간만으로는 화면을 채우기 어려웠다. 이 가설의 가치는 게시물 쪽 정보에 있다.

### 1차 검증: 사용자 10명 테스트

- 참여자 1명당 본인이 최근 저장한 맛집·카페 게시물 2~3개, 총 약 25건으로 진행한다.
- 표본이 작으므로 아래 수치는 통과·실패 판정보다 방향 판단용이다. 인터뷰 내용을 함께 본다.

| 지표 | 기준 | 측정 방법 |
| --- | --- | --- |
| 장소 매칭 | 70% 이상이 수정 없이 맞는 장소(또는 목록 안에 정답) | `place_matched` / `place_match_corrected` 이벤트 |
| 판단 완료 | 80% 이상이 저장 또는 관심 없음 선택 | 이벤트. 진행자가 판단을 요청하므로 실제보다 높게 나온다는 점을 감안 |
| 추가 검색 없이 판단 | 60% 이상이 "이 화면만으로 판단할 수 있었다" | 사용 후 인터뷰 (15장) |
| 외부 지도 이동 사유 | 사유별 비율 | 의도별 버튼 이벤트 (`external_map_opened.reason`) |
| 판단 시간 | 베이스라인보다 짧음 | 테스트 전 기존 방식 판단 시간 측정 (15장) |

개발 완료 조건(수집 성공, 응답 시간, 저장 동작 등)은 12장에서 따로 관리한다.

## 3. 범위

### MVP에 포함

- 인스타그램 게시물·릴스 URL 입력과 정규화 (`img_index` 보관 포함)
- 이전에 확인된 같은 링크의 결과 즉시 조회 (단순 캐시)
- 서버에서 공개 메타데이터(`og:description`, `og:image`) 수집
- LLM으로 단서 추출: 장소 목록, 지역, 메뉴, 가격, 추천 이유, 방문 팁, 협찬 여부, 장소 콘텐츠 여부
- 단서가 없을 때 이미지 OCR: 커버 이미지와 `img_index`가 가리키는 이미지, 최대 2장
- 대체 경로: 캡션 붙여넣기, 직접 장소 검색
- 장소 확인: 한 곳 확인, 여러 곳 목록에서 선택, 체인 지점 목록에서 선택
- 범위 밖 게시물 안내
- 결과 화면: 게시물에서 뽑은 정보 + 카카오 기본 장소 정보 + 외부 지도 연결
- 브라우저에 가볼 곳·관심 없음·방문 완료 상태 저장, 원본 링크 연결
- 분석·판단 이벤트 기록

### MVP에서 제외

- 영상 업로드와 영상 분석(프레임 추출, 음성 전사, 작업 큐·워커) — Phase 0에서 필요성 확인되지 않음
- 공유 매핑 신뢰도 계산(확인·수정 이력 기반)
- Google Places 연동 (평점 보조 표시는 후속 판단)
- 여러 곳을 한 번에 저장
- 회원가입, 로그인, 기기 간 동기화
- 팔로우, 피드, 댓글 등 소셜 기능
- 개인화 추천, 알림, 예약, 리뷰 작성
- 맛집·카페 외 카테고리, 인스타그램 외 SNS
- 네이티브 앱과 인스타그램 공유 메뉴 연동
- 해외 장소 검색
- 사용자 계정으로 인스타그램에 로그인하는 비공식 수집

## 4. 사용자 경험과 화면

### 4.1 홈

- 제목: "마음에 든 장소, 바로 확인해 보세요"
- 인스타그램 링크 입력창, 기본 버튼 "장소 찾기"
- 보조 링크: "캡션을 붙여넣을게요", "장소를 직접 검색할게요"
- 하단 이동: 홈 / 가볼 곳

### 4.2 분석 진행

- 링크 경로는 5초 안에 끝나는 것을 목표로 한다. 이미지 OCR까지 가면 15초 안을 목표로 한다.
- 진행 상태는 "게시물 읽는 중 → 장소 찾는 중" 두 단계로 단순하게 보여준다.
- 같은 입력이 이미 처리 중이면 새 요청을 만들지 않는다.

### 4.3 장소 확인

자동 결과를 확정 사실처럼 다루지 않는다. 경우에 따라 세 가지 화면을 쓴다.

| 경우 | 화면 |
| --- | --- |
| 장소 1곳 | "이 장소가 맞나요?" + 후보 2~3개, "다른 장소 검색", "여기에 없어요" |
| 여러 곳 모음 | "이 게시물에는 N곳이 있어요" 목록. 사용자가 저장할 곳을 하나 고른다. `img_index`로 읽은 이미지의 장소를 먼저 보여준다 |
| 체인점 | "OO는 지점이 N개 있어요" 지점 목록. 사용자가 고른다 |

범위 밖 게시물이면 "맛집·카페 게시물이 아닌 것 같아요"를 보여주고 "그래도 장소 검색하기"를 제공한다. 실패 화면처럼 보이지 않게 한다.

### 4.4 판단 결과

게시물에서 얻은 정보를 위에, 지도 정보를 아래에 둔다.

1. 장소명, 지역, 카테고리, "장소 변경"
2. **게시물에서 추천한 이유** (1~2문장 요약)
3. **추천 메뉴와 가격** (게시물에 언급된 것만)
4. **방문 팁** (웨이팅, 주차, 유아의자, 점심특선 등 게시물에 언급된 것만)
5. **협찬 게시물 표시** (확인된 경우)
6. 기본 정보: 주소, 전화번호 (카카오)
7. 영업시간: "카카오에서 영업시간 보기" 링크. 캡션에 영업시간이 있으면 "게시물에서 언급 (게시일 YYYY.MM.DD)"으로 따로 표시
8. 외부 지도 버튼: "메뉴 더 보기", "리뷰 보기", "길찾기" — 버튼별로 이동 사유를 기록
9. "가볼 곳 저장" / "관심 없음"

없는 정보는 추측하지 않고 항목을 숨기거나 "정보 없음"으로 표시한다. 게시물에서 온 정보와 지도에서 온 정보는 출처를 구분해 보여준다.

### 4.5 가볼 곳

- 가볼 곳과 방문 완료 상태, 장소 핵심 정보, 처음 발견한 인스타그램 링크, 외부 지도 열기
- 같은 장소를 다른 게시물로 다시 저장하면 장소 1개에 원본 링크를 여러 개 연결한다.
- 저장 위치 안내: 브라우저 데이터 삭제, 기기 변경, iOS Safari의 장기 미방문 시 데이터 삭제, 인스타그램 인앱 브라우저와 Safari의 저장소가 다르다는 점을 첫 저장 때 짧게 알린다. 홈 화면에 추가를 권한다.

## 5. 핵심 사용자 흐름

### 링크 흐름 (기본)

1. 사용자가 인스타그램 URL을 붙여넣는다.
2. 서버가 URL을 정규화하고 `img_index`를 따로 보관한다.
3. 캐시에 같은 게시물의 확인된 결과가 있으면 바로 보여준다.
4. 서버가 공개 메타데이터에서 캡션과 커버 이미지 주소를 읽는다.
5. LLM이 캡션에서 단서를 구조화하고 장소 콘텐츠 여부를 판단한다.
6. 장소 단서가 있으면 장소를 검색하고(8장 규칙), 장소 확인 화면으로 간다.
7. 사용자가 확인하거나 수정하면 결과 화면을 보여주고, 저장 또는 관심 없음을 받는다.

### 단서가 부족한 흐름

1. 캡션에 장소 단서가 없으면 커버 이미지와 `img_index` 이미지를 OCR로 읽는다.
2. OCR 결과로 다시 단서를 추출한다.
3. 그래도 없으면 "게시물에서 장소를 찾지 못했어요"와 함께 캡션 붙여넣기, 직접 검색을 제시한다.
4. 이후 장소 확인과 결과 화면은 같다.

### 여러 곳·체인 흐름

1. 단서에 장소가 2곳 이상이면 목록 화면을 보여준다.
2. 사용자가 한 곳을 고르면 그 장소로 결과 화면을 연다. 다른 곳은 목록으로 돌아가 다시 고를 수 있다.
3. 한 상호로 지점이 여러 개 검색되고 지역 단서로 좁혀지지 않으면 지점 목록을 보여준다.

## 6. 시스템 구성

### 기술 구성

- 모바일 웹: Next.js, TypeScript
- 서버 API: Next.js Route Handler (BFF)
- 공유 데이터: Supabase Postgres (캐시와 이벤트)
- 개인 목록: 브라우저 localStorage 또는 IndexedDB
- LLM: 구조화 출력(JSON 스키마)과 이미지 입력을 지원하는 모델. MVP는 Gemini API 무료 등급(Flash-Lite)으로 시작하고, 정확도가 부족하면 상위 모델로 바꾼다
- OCR: 이미지 2장 이내이므로 별도 워커 없이 API 요청 안에서 처리. 응답 시간이 목표(15초)를 넘으면 그때 비동기로 바꾼다.

v1의 영상 임시 저장소, 작업 큐, 영상 분석 워커는 제거한다.

### 주요 컴포넌트

1. `SourceNormalizer` — 추적 파라미터 제거, `/p/`·`/reel/`·`/계정명/p/` 통일, `img_index` 분리. `spikes/og-probe/lib/probe.js`의 `normalize`를 옮긴다.
2. `MetaFetcher` — `og:description`, `og:image` 수집. 모바일 브라우저 UA로 먼저 요청하고 실패하면 링크 미리보기 크롤러 UA로 한 번 더 요청한다. 요청 간격 제한과 캐시로 반복 요청을 줄인다.
3. `ClueExtractor` — 캡션(또는 OCR 텍스트)을 LLM으로 구조화한다 (7장 스키마).
4. `ImageOcr` — 커버와 `img_index` 이미지의 글자를 읽는다.
5. `PlaceProvider` — 키워드 검색, 주소 검색, 외부 지도 URL 생성. MVP는 `KakaoPlaceProvider`만 구현한다.
6. `CandidateRanker` — 8장 규칙으로 후보를 합치고 순위를 매긴다. 체인 여부를 판단한다.
7. `MatchCache` — 같은 게시물의 확인된 결과를 저장하고 재사용한다.
8. `DecisionView` — 출처를 구분해 정보를 보여주고 판단을 기록한다.

### 데이터 흐름

`링크 입력 → 정규화 → 캐시 조회 → 메타 수집 → 단서 추출 → (없으면) 이미지 OCR → 장소 검색·순위화 → 장소 확인(1곳 / 목록 / 지점) → 결과 화면 → 로컬 저장 + 이벤트`

## 7. 콘텐츠 분석 원칙

### 인스타그램 메타데이터

- Phase 0에서 로그인 없이 서버(데이터센터 IP)에서 13/13 캡션을 받았다. 다만 1회 측정이고 정책 변경으로 언제든 막힐 수 있으므로 대체 경로를 유지한다.
- 비공식 로그인 세션, 우회 수집, 화면 전체 스크래핑은 쓰지 않는다. 공개 메타 태그만 읽는다.
- 캡션 원문은 분석에만 쓰고 공유 데이터로 영구 저장하지 않는다.

### LLM 구조화 출력 스키마

```
is_place_content: boolean          // 맛집·카페 게시물인가
places: [{
  name: string                     // 상호
  branch_hint: string | null       // "본점", "망원점" 등
  region_hint: string | null       // 게시물 표현 그대로: "경대정문", "망원"
  region_normalized: string | null // 행정구역: "대구 북구", "서울 마포구"
  address: string | null           // 게시물에 적힌 주소
  menus: [{ name, price | null }]
  reason: string | null            // 추천 이유 요약
  tips: string[]                   // 웨이팅, 주차, 유아의자 등
  hours_mentioned: string | null   // 게시물에 적힌 영업시간
}]
is_sponsored: boolean | null       // 협찬·광고 표기
evidence: 각 필드의 근거 (caption / ocr)
confidence: number
```

- 형식 검증에 실패하면 제한 횟수만 다시 시도하고, 이후에는 직접 검색으로 안내한다.
- 영업시간, 평점, 주소를 AI가 만들어내지 않는다. 게시물에 적힌 값은 "게시물에서 언급"으로만 표시한다.

### 이미지 OCR

- 대상: 커버(`og:image`), 그리고 공유 링크에 `img_index`가 있으면 그 이미지. 최대 2장.
- OCR 텍스트는 캡션과 같은 스키마로 다시 추출한다.
- 이미지 원본은 저장하지 않는다.

## 8. 장소 제공자와 검색 규칙

### 국내 MVP: 카카오

카카오 로컬 API에서 장소 식별자, 이름, 카테고리, 주소, 좌표, 전화번호, 장소 페이지 링크를 가져온다. 영업시간·메뉴·평점은 API에서 제공되지 않으므로 카카오 장소 페이지로 연결한다.

### 검색·매칭 규칙 (`CandidateRanker`)

1. 음식점·카페 카테고리로 필터한다. (나랑가: 필터 없이는 협동조합이 1위)
2. 장소마다 "상호만"과 "지역어 + 상호" 두 가지로 검색한다. (장군닭발은 지역을 붙이면 놓치고, 아이안은 붙여야 1위)
3. 주소가 있으면 주소로도 검색한다. (서울곱창: 상호만으로 전국 1,566건, 주소로는 1위)
4. 지역 힌트는 주소 문자열과 직접 비교하지 않는다. LLM이 행정구역으로 바꾼 값과 카카오 검색의 지역 인식을 활용한다. (망원 → 실제 지번은 성산동)
5. 주소 비교는 도로명과 건물번호 앞부분까지만 맞춘다. (평교로 26-1 vs 26)
6. 두 검색 결과에 모두 나온 장소를 우선한다. 같은 상호가 여러 지점이고 지역 단서로 좁혀지지 않으면 체인으로 보고 지점 목록을 보여준다.

### 해외 확장

`PlaceProvider` 인터페이스와 내부 `placeId`만 유지한다. 장소 하나에 제공자별 식별자를 여러 개 연결할 수 있게 한다. 시간대·통화 등 해외 전용 필드는 출시 시점에 추가한다.

## 9. 데이터 모델과 저장 정책

### 서버 데이터

#### `sources`

- `id`, `platform`(`instagram`), `source_type`(`post` / `reel`), `normalized_key_hash`, `created_at`

#### `places`

- `id`(내부), `country_code`, `name`, `category`, `address`, `latitude`, `longitude`, `map_url`, `refreshed_at`

#### `place_sources`

- `place_id`, `provider`, `provider_place_id`, `last_verified_at`

#### `source_place_matches`

- `id`, `source_id`, `place_id`
- `position`: 게시물 안에서의 순서 (여러 곳 모음 지원)
- `status`: `unverified` / `user_confirmed`
- `confirmation_count`, `correction_count`
- `extraction_summary`: 추천 이유·메뉴·가격·방문 팁의 짧은 요약 (캡션 원문 아님)
- `created_at`, `updated_at`

v1의 `match_revisions`(수정 이력 기반 신뢰도)와 `analysis_jobs`(영상 비동기 작업)는 MVP에서 제외한다. 처리 중복 방지는 요청 단위 잠금으로 처리한다.

#### `events`

- 익명 기기 식별자의 해시, 이벤트 이름, 선택적 source/place 식별자, 최소한의 메타데이터, `created_at`

### 브라우저 데이터

- 내부 장소 식별자와 화면 표시용 최소 스냅샷
- 원본 인스타그램 URL 목록 (장소 1개에 여러 개 가능)
- 저장 시각, 상태(가볼 곳 / 방문 완료)

### 개인정보와 보안

- 캡션 원문, OCR 원문, 이미지 원본은 영구 저장하지 않는다.
- 공유 데이터는 서버 API로만 수정하고 직접 DB 쓰기를 노출하지 않는다.
- 익명 쓰기 API에 요청 제한, 입력 검증, 중복 방지를 적용한다.
- 메타 수집기는 인스타그램 도메인만 요청한다 (임의 URL 대리 요청 금지).
- 로그에 전체 캡션을 남기지 않는다.
- LLM에는 공개 게시물의 캡션·이미지만 보내고 사용자 정보(기기 식별자, 저장 목록 등)는 보내지 않는다. 무료 등급 LLM은 입력이 제공자의 제품 개선에 쓰일 수 있으므로, 사용자 테스트 안내와 개인정보 안내에 외부 AI 서비스 사용을 알린다.

## 10. 오류와 복구

| 상황 | 처리 |
| --- | --- |
| 잘못된 URL | 입력값 유지, 게시물·릴스 링크 형식 안내 |
| 메타 수집 실패·차단 | 크롤러 UA로 1회 재시도 후 캡션 붙여넣기·직접 검색 제시 |
| 캡션에 단서 없음 | 이미지 OCR → 그래도 없으면 캡션 붙여넣기·직접 검색 |
| 범위 밖 게시물 | "맛집·카페 게시물이 아닌 것 같아요" + "그래도 장소 검색하기" |
| 여러 곳 모음 | 목록에서 선택 |
| 체인 지점 구분 불가 | 지점 목록에서 선택 |
| 카카오에 없는 장소(신규·팝업) | "아직 지도에 등록되지 않았을 수 있어요" + 직접 검색, 게시물 정보만으로 저장 허용 |
| LLM·카카오 일시 실패 | 제한적으로 재시도 후 직접 검색 |
| 일부 정보 없음 | 해당 항목 숨김, 외부 지도 버튼 유지 |
| 브라우저 저장 실패 | 저장되지 않았음을 알리고 재시도 제공 |

핵심 원칙은 자동 분석 실패가 수동 장소 저장을 막지 않는다는 것이다.

## 12. 테스트와 완료 조건

### 자동 테스트

- URL 정규화: 게시물·릴스·`/계정명/p/`, 추적 파라미터, `img_index`, 잘못된 도메인 (`og-probe` 테스트 이관)
- 메타 파싱: HTML 엔티티, 캡션 안의 따옴표, 캡션 없음
- LLM 스키마 검증: 누락 필드, 잘못된 타입, 재시도 종료
- 검색 규칙: Phase 0 사례(장군닭발, 아이안, 나랑가, 서울곱창, 이현김밥 주소, 고봉당 체인)를 고정 테스트로 사용
- 여러 곳·체인 목록 생성
- 로컬 저장: 저장, 관심 없음, 방문 완료, 원본 링크 여러 개 연결
- 모바일 E2E: 링크 → 저장, 단서 없음 → 직접 검색 → 저장, 여러 곳 → 선택 → 저장

### 개발 완료 조건

- Phase 0 샘플 13개 중 장소가 있는 12개에서 링크 입력부터 장소 확인 화면까지 동작한다 (고봉당은 지점 목록).
- 링크 경로 응답 5초, OCR 경로 15초 안 (p90 기준).
- 메타 수집 실패 시 대체 경로가 동작한다.
- 로그인 없이 저장·방문 상태 변경·원본 링크 열기가 동작한다.
- 2장의 지표를 10명 테스트에서 측정할 수 있다.

## 13. 단계별 출시

### 1단계: 국내 모바일 웹 MVP

1-1. 링크 → 캡션 → 단서 → 카카오 → 장소 1곳 확인 → 결과 → 저장
1-2. 여러 곳 목록, 체인 지점 목록, 범위 밖 안내
1-3. 이미지 OCR, 캡션 붙여넣기·직접 검색
이후 10명 테스트

### 2단계: 공유 메뉴 연결

네이티브 앱 또는 공유 확장을 추가해 인스타그램 공유 메뉴에서 바로 링크를 넘긴다. 분석·확인·저장 흐름은 그대로 쓴다.

### 3단계: 해외 맛집·카페

국가별 `PlaceProvider`를 추가한다.

### 후속 판단 항목

- 메타 수집이 실사용 규모에서도 안정적인가 (차단률 추적)
- 이미지 OCR로도 못 찾는 비율이 영상 분석을 정당화할 만큼 큰가
- Google 평점(리뷰 30개 이상만)을 보조로 보여줄 가치가 있는가
- 여러 곳을 한 번에 저장하는 기능이 필요한가
- 공유 메뉴가 링크 붙여넣기보다 전환을 크게 개선하는가
- 로그인과 기기 간 동기화가 필요한가

## 14. 확정된 제품 원칙

- 자동 추출 뒤 사용자 확인·수정을 반드시 거친다.
- 틀린 정보보다 빈 정보를 선택하며, 없는 정보는 만들지 않는다.
- 게시물에서 온 정보와 지도에서 온 정보는 출처를 구분해 보여준다.
- 비공식 인스타그램 수집을 제품의 기반으로 삼지 않는다. 공개 메타 태그만 읽는다.
- 동일 링크의 결과는 캐시로 재사용해 반복 요청을 줄인다.
- 개인 저장 목록과 원본 링크는 로그인 없이 사용자 브라우저에 둔다.
- 자동 분석 실패가 수동 저장을 막지 않는다.

## 15. 사용자 테스트 계획

### 참여자와 진행

- 10명. 맛집 계정을 팔로우하지 않는 사람을 3명 이상 포함한다.
- 각자 인스타그램 저장됨 목록에서 최근 맛집·카페 게시물 2~3개를 고르지 않고 순서대로 가져온다.

### 베이스라인 (Moumm 사용 전)

게시물 1개로 평소 방식대로 방문 여부를 판단하게 하고, 걸린 시간과 연 앱·검색 횟수를 기록한다.

### 과제

> 저장해 둔 맛집·카페 게시물 링크를 넣어보세요. 결과 화면만 보고 이곳을 가볼 곳으로 둘지 판단해 주세요.

### 사용 후 질문 (Notion 기준 문서)

1. 이 화면만 보고 갈지 판단할 수 있었나요?
2. 추가로 확인하고 싶은 정보는 무엇이었나요?
3. 다른 앱을 열고 싶었다면 어디를 왜 열고 싶었나요?
4. 기존 방식보다 편해진 부분이 있었나요?
5. 없어도 괜찮았던 정보는 무엇인가요?

### 결과에 따른 다음 결정

- 추가 검색이 크게 줄어듦 → 정보 통합 가설 유효, 2단계 검토
- 대부분 여전히 지도 앱으로 이동 → 이동 사유(메뉴·리뷰·길찾기)를 보고 결과 화면 보강
- 기존 방식도 충분히 편함 → 문제 강도가 약함, 다른 문제 후보 탐색
